# Beamal UI／UX 與產品設計品質標準

日期：2026-10-15。這是本專案的工作及驗收標準，不是完成報告或無障礙認證。

## 目標及使用者

UI（畫面）與 UX（整個操作體驗）的品質，與功能正確性同等重要。交付要讓客戶知道在哪裡、下一步做甚麼、操作結果是甚麼，並能自然完成工作；不能只把所有按鈕放進畫面就算完成。
沿用 Beamal 美術風格、圖片、中英文及手機版；SchoolTracs 用作已查證功能的參考，畫面組織仍須按 Beamal 使用者的工作需要判斷。
已確認規模為約四位老師（包括可授課的管理員）、300 位活躍學生、六種課程，學生年齡約 3–18 歲。角色包括管理員兼老師、普通老師、學生帳戶。
「多數由家長代孩子操作」「老師主要在課前用手機」等仍是待研究假設；不能把年齡、示例帳戶或 Agent 推測當成真實訪談結果。

## 已查閱的設計原則及證據界線

| 來源 | 採用原則及本專案應用 |
|---|---|
| [GOV.UK：了解使用者需要](https://www.gov.uk/service-manual/user-research/start-by-learning-user-needs) | 先了解誰要完成甚麼、目前怎樣做及遇到甚麼困難；非使用者提供的意見先列為假設，持續觀察與驗證。 |
| [NN/G：任務分析](https://www.nngroup.com/articles/task-analysis/) | 把目標拆成有起點、終點及順序的工作；例如目標是安排上課，不是填完一張表。Agent 模擬操作不能代替觀察實際使用者。 |
| [NN/G：十項易用性原則](https://www.nngroup.com/articles/ten-usability-heuristics/) | 狀態清楚、使用熟悉用語、可取消、操作一致、預防錯誤、減少記憶負擔；優先突出當前工作所需內容。這是評估原則，不是使用者研究結果。 |
| [NN/G：三次點擊規則並不成立](https://www.nngroup.com/articles/3-click-rule/) | 不訂所有工作必須三次點擊完成。應同時看理解難度、尋路、等待、輸入、錯誤及返回成本。 |
| [Design Council：Double Diamond](https://www.designcouncil.org.uk/resources/the-double-diamond/) | 先理解及定義問題，再發展、試驗及改善方案；遇到新證據可以回到前一步。下面六步是本專案的具體工作方式。 |
| [W3C：目標大小 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) | AA 條件的指標目標通常至少 24×24 CSS 像素，另有間距、等效操作、行內連結等例外，須逐項核對；不能把畫面看來夠大當成通過。 |
| [W3C：重複輸入 3.3.7](https://www.w3.org/WAI/WCAG22/Understanding/redundant-entry.html) | 同一流程已提供而再次需要的資料，應預填或可選取；必要、安全或資料已失效等情況有例外。預填仍須遵守角色及私隱限制。 |
| [W3C：焦點可見 2.4.7](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html) | 使用鍵盤時須看得到目前選中的控制項；焦點指示不能自行消失。彈窗返回等細節另按本專案下列標準檢查。 |

以上來源支持原則；本文件提出的像素、測試尺寸及驗收門檻是專案決策，不是來源替 Beamal 訂出的標準。閱讀文章、程式測試或幾項檢查，均不能宣稱已精通 UX、已完成真實用戶研究或全面符合 WCAG。

## 每項工作的設計循環

1. **理解**：先問角色今天要做甚麼、為甚麼、多久做一次、用哪個裝置；整理使用者回饋、已觀察行為、參考系統及待驗證假設。
2. **定義**：寫清主要任務、資料與權限、起點及成功結果；區分每日工作和低頻設定，找出重複輸入、跨頁尋找及容易做錯的決定。
3. **設計**：先畫任務順序和資訊分組，再安排主要操作、欄位、詳情及返回路徑；必要時比較兩個小方案，保留選擇理由。
4. **實際走一次**：用對應角色、正常資料量及真實畫面完成任務，包含錯誤、取消、返回及重開；記錄停頓、誤解、繞路和結果證據。
5. **獨立審查**：由未製作該段介面的 Agent，按同一任務卡重做並核對資料與畫面；它是獨立工程審查，不能標成客戶測試。
6. **迭代**：先修無法完成、誤導及資料風險，再修多餘操作與視覺細節；重做受影響任務。實際使用者參與後，另記角色、情境、觀察及限制。

## 任務卡範本

### 參考 SchoolTracs 時的第一性原理檢查

每次先實際走對應流程，再拆成「用戶目標、必要資料、限制、最小可靠操作」，最後才決定按鈕及頁面位置。參考已有產品時，要理解做法帶來的效果；不預設現有排法一定最適合 Beamal，也不因追求少按幾下而省略修改範圍、金額或權限等必要確認。

- **先看實際行為**：記錄入口、預選資料、主次操作、展開／取消／返回及結果，保留當次畫面。不能只憑截圖外觀、舊筆記或記憶判定流程。
- **再解釋原因**：逐項寫「這個安排解決甚麼問題」「為甚麼在此處需要它」「移走或合併會有甚麼代價」。從畫面推斷的設計理由標成推論，不當作 SchoolTracs 設計者已證實的原意。
- **分清任務及資料層級**：課程的基本設定、整套定期排課、某日某堂的名冊及學生訂單各有對象；跳頁保留已確認的課程、日期、課次及來源位置，低頻設定放回所屬對象。
- **比較 Beamal 的現況與方案**：保留有用的關聯、可見結果及安全確認；改善沒有幫助的重選、搜尋、返回及純描述文案。保留 Beamal 視覺風格、雙語、手機與三種角色。
- **讓另一位 Agent 反問**：使用者只是查看，為何進了編輯？已選了這堂，為何還要找一次？這個步驟能否刪除，刪除會否造成誤改、錯人或錯誤付款？再以真正畫面重做任務。

當次方法示例：[SchoolTracs 課程與時間表操作研究](reference-ux-reasoning-20261015.md)。這個研究流程是後續逐頁工作的要求，不代表所有頁面已完成。

情境與目標：當……，我需要……，以便……。

## 優先任務與資訊分組

| 工作範圍 | 使用者任務 | 主要路徑與應保留的上下文 |
|---|---|---|
| Student／學生帳戶 | 找下一堂、查看課程與付款、提出調課或病假 | 時間表／課程 → 指定課堂 → 詳情或申請 → 清楚結果；返回原月份、選中課堂及申請內容。家長與孩子操作差異待研究。 |
| Staff／員工 | 找某老師、查看任教安排、調整個人工作權限 | 員工 → 老師 → 對應詳情；登入帳戶連結另放清楚的進階入口。普通老師只見自己／獲授權內容，不靠前端隱藏代替權限。 |
| Courses／課程 | 建立或修改課程、理解收費、安排該課程上課 | 課程清單 → 課程 → 費用／新增排課；沿用所選課程，不要求重新搜尋或輸入同一資料，返回保留篩選。 |
| Timetable／時間表 | 找某日／老師的課堂、看名冊、修改一堂或往後課堂 | 日期及必要篩選 → 課堂 → 名冊／修改 → 原時間表；清楚顯示修改範圍。低頻資源設定放 Settings，不擠在每日工具列。 |

這是根據已確認要求提出的任務圖，不代表已觀察四位真實老師或 300 位真實學生。其餘頁面沿用同一分析方式，並非只驗收上述四頁。

## 每頁必做的驗收

| 項目 | 驗收方式及預期效果 |
|---|---|
| 留白、對齊及層級 | 本專案主要內容區預設桌面左右至少 24px、手機 16px；相同區塊沿用一致間距。標題、標籤、內容、圖示與操作列有可見對齊關係，沒有貼邊或裁切。必要例外記錄理由。 |
| 主要操作 | 使用者能分辨當頁主要工作；低頻及進階功能有合理歸屬。必要功能搬位置時保留可找到的入口，不能以減少按鈕為由移除實際能力。 |
| 響應與縮放 | 實際核對 390px 手機、768px 及 1280px 畫面，中英文均沒有頁面級橫向溢出、標籤重疊或主按鈕遮擋；闊表格可在自身區域捲動。另看放大文字後可否操作。 |
| 用語與雙語 | 同一概念名稱一致；以中心工作用語命名。中英文不靠固定寬度勉強塞入，較長名稱、日期及金額仍可讀，重要含義不能只靠顏色或圖示。 |
| 頁首文案 | 頁名已清楚表達用途時，不加重複介紹、口號或泛用副標題。只有能幫助當前決定或操作的資訊才保留，例如目前人物、日期範圍、實際狀態或必要限制；必要提示放在相關操作附近。 |
| 鍵盤及觸控 | Tab 順序符合閱讀及操作順序，焦點可見；彈窗開啟後不跳到背景，關閉回原入口。拖動有可理解的等效操作。主要觸控按鈕以 44×44 CSS 像素作專案設計目標，並逐項核對 W3C 最低條件及例外。 |
| 載入及空狀態 | 能分辨正在讀取、真正沒有資料、篩選無結果及讀取失敗；不先顯示假零筆或其他帳戶的舊資料。空狀態提供當下合理的下一步。 |
| 表單及錯誤 | 必填與格式清楚；同一流程不無故重填。錯誤貼近欄位並提供解法，重試保留草稿；背景更新不蓋過正在輸入的內容。 |
| 進行中及成功 | 提交即有回饋並防止重複提交；實際保存才寫「已儲存」，實際收款狀態才寫 Paid。失敗、未完成及需要確認不能使用同一成功樣式。 |
| 返回與延續 | 取消、關閉、儲存及返回後，保留合理的日期、搜尋、篩選、分頁和捲動位置；重新開啟能分辨已保存資料與未保存草稿。 |
| 導覽一致 | 窄畫面選取可前往的側欄頁面後，選單一律收起，讓內容可見；包含有獨立網址的費用頁。桌面保留原有展開／收起選擇；未獲准前往的項目不改變當前頁面或選單狀態。 |
| 示範的真實感 | 人名、課名、課室及說明採自然中心示例，不把 QA、檢查名稱、資料 ID 或「虛構」字尾塞進日常名稱。以低干擾「示範環境」標示環境；未接通的行為仍須如實說明，不暗示已保存、寄出或收款。 |

## 操作成本及測量

不使用所有任務通用的三次點擊上限。需要確認修改範圍或付款結果的步驟可以保留；應刪除的是沒有幫助的繞路、重填、等待及不清楚的選擇。

| 測量 | 記錄方法 |
|---|---|
| 任務完成與理解 | 是否不用提示完成；能否說出處理了哪一位學生／哪堂課、結果及下一步。Agent 結果與實際使用者結果分開。 |
| 操作及決定成本 | 記錄必要點擊、選擇次數、重複輸入、無效返回及另找資料次數；比較同一任務改動前後，不能只比較點擊總數。 |
| 時間與流暢度 | 記錄找入口、輸入、等待及完成時間，以及卡頓位置；重複測量時報中位數及較慢的 95% 分位數，附裝置、資料量及測量次數。小樣本不作人口推論。 |
| 恢復能力 | 故意輸入錯誤、取消、重試及返回，記錄是否丟草稿、重複產生資料或找不到原工作；付款及跨角色改動另核對實際資料。 |

專案初步門檻：主要任務不得有未修正的無法完成、錯誤角色資料、誤導成功、重複付款或草稿遺失；上述尺寸下不得有遮擋主要操作的排版問題。日常重複任務的無必要重填目標為零，例外逐項說明。
完成時間及操作數先建立現況基線，再按任務提出改善目標；尚未量度時填「未量度」，不能先寫提升百分比、通過率或「零卡頓」。這些門檻是本專案建議，不是已完成研究得出的普遍定律。

## 階段、證據及交付

- **目前優先完成所有 UI 的樣式及流程**，後續功能接駁的次序不變；完整 Goal 仍包含 SchoolTracs 已確認功能與 Notion 要求。
- 分別記錄「功能對齊」「UI 實作」「實際畫面走查」「共用資料及權限」「真實使用者研究」。某一項完成不能代替其他項。
- 300 位名冊示例不等於 300 位已付款學生或 300 人同時操作；畫面使用同一共用資料才可聲稱跨角色同步。
- 程式測試及 build 只證明其覆蓋範圍；未實際看過的版面標「未目視驗收」。工具故障、未測功能及重要差異記錄限制，不填成通過。
- 每頁審查保存任務卡、角色／尺寸／語言、操作步驟、可重現問題、影響與修正後證據；先修阻擋客戶工作的問題，再改善操作成本及視覺細節。
- 本標準隨實際觀察迭代；沒有做過的客戶訪談、無障礙測試或跨裝置驗證不補寫成已完成。主要目標是客戶能清楚、可靠、順暢地完成工作。
