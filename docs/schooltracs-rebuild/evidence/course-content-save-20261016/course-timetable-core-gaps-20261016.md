# Course / Timetable: five highest-impact core gaps

Read-only code/tests/docs audit. Committed baseline: 9aa80f0; Root is already implementing Course-content persistence in the working tree. This audit does not modify the Goal, repository or database, operate a browser or run a test suite. File/line pointers below refer to the inspected baseline; function names remain the useful anchors while Root's Course-content work shifts later lines.

## Priority and immediate delivery boundary

| Priority | Core gap and practical impact | Immediately useful complete increment |
|---|---|---|
| 1 — Root already owns this | Course introduction/recommended ages have a complete editor but no committed save/read projection. Teachers and visitors cannot see an Admin's confirmed content from the same source. | Save exact Course content with its version, acknowledgement and audit; re-read through the scoped catalogue and explicit public projection, preserve existing fees/schedules and old drafts on409. Root's current working-tree save functions/tests are in progress, not independently verified by this audit. |
| 2 | Responsible teachers cannot actually record a student's attendance, Remark, Sticker or timetable-display preference. Every apparent Save is disabled and reload restores the original unmarked state. This blocks daily teaching. | Persist the exact student-session's attendance and annotation with a version and audit, then read the same saved record into roster/teacher UI and the allowed own-student attendance projection. Do not automatically deduct quota, release seats or change class Full. This known recording operation need not wait for unconfirmed deduction policies. |
| 3 | Student sick/rescheduling requests and teacher Pending Confirmation arrangements never become durable requests or a real assigned follow-up. A parent and teacher cannot continue the same case across logins. | Save the exact owned child's original session request / Pending case and one corresponding durable teacher follow-up; after restart both sides read that same case. Pending must not pick a destination, hold a place, release the original seat or count as confirmed rescheduling. Actual target selection/Confirm then requires the declared eligibility source and the still-pending topic/window/cutoff policies. |
| 4 | Date / exact-lesson internal notes are lost when closed. The input/review/return UI exists, but the final save command is deliberately inert. | Persist exact lesson notes first with author/version/audit and the declared internal read/write scope, reuse current context/return safeguards and keep them out of student/public DTOs. Date notes require an explicit owner/shared-date scope: a visible empty teacher day currently authorizes composing only, not shared writing. This distinction must remain explicit. |
| 5 | Public timetable → exact Trial slot → registration form cannot submit an application or reserve/release its matching quota. The visible main intake path stops at Review. | Add an explicit trial application store and authenticated/anonymous submission boundary with atomic source/quota recheck, idempotency, durable application+matching hold and later release/reject. Existing Trial/Rescheduling holds are readable infrastructure, not a booking implementation. Before enabling the final action, settle the few indispensable registration/Total-quota rules; do not silently bypass Total or treat published visibility as booking permission. |

The first four permit bounded useful persistence work now without inventing quota deductions or mass rescheduling. Priority5 is a core required flow, but unlike a pure text save it cannot honestly be enabled while its booking policy is unknown. Its source validation, transaction, failure and replay scaffolding can be implemented first. This is a named dependency, not a reason to label the whole feature minor or finished.

## What is already implemented and should not be re-listed as missing

Source verification shows real schedule APIs for whole-series and single/future mutation/cancellation/restoration (`api-client.js:193–205`, schedules/server tests). Internal day/week/range/month/list, exact Course→Timetable/month/lesson return, Course/Fee current saves/lifecycle and exact shared paid roster/own-Student timetable reads exist. New work should build on them, not replace them with a second fictional system.

Age from the paid batch filter-facts source is already merged into the canonical exact lesson student in `sharedLessonSnapshot`; do not reopen that solved source gap. Package remaining/validity/components and future fee pricing still have real unfinished work, but their amount/deduction/owner/effective-price policies should not be silently resolved inside attendance or note saves.

The demo code explicitly says only Chloe has paid enrollment (`server/relational-demo.mjs:106–125`); the other299 active profiles are not300 paid histories. This is a source-code limitation, not an observation of the live database. Final scale acceptance must use the formal order/payment/session path (`enrollment-orders.test.mjs:45,70,79,86`), never direct Paid/session seeding. No live data count was inspected in this audit.
