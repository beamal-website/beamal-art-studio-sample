# 共用中心示例資料

`sample/server/relational-demo.mjs` 是明確執行的本機示例工具，不會隨網站啟動，不會重設資料庫、帳戶或密碼。它只重用提供的課程、費用、老師及課室 ID；不按同名資料猜配。

建立範圍：

- 四個教師資源：Maya（管理員兼老師）、Leo（老師登入）、Ava、Ethan。Ava／Ethan 不新增登入帳戶。
- 300 個正式學生檔案，包括原有 Chloe 及 299 個新檔案，建立時年齡為 3–18 歲，退學日期留空。
- 六個既有課程及明確指定的費用；這裡是 `courses`，不是排課政策 `class_types`。
- 保留 Leo 的 `DEMO_IDS.schedules.leo` 與 Maya 的既有排課，不重建或改動。另建立五套每週四堂的排課，Leo／Maya／Ava／Ethan 分配為 1／2／1／1 套，每班上限不超過 8 人或所選課室容量。
- Chloe 連到原有學生登入帳戶，報讀 Leo 原有課堂及新增課堂。原始示例通常得到 **2 筆 Paid 訂單、7 個學生課節**；已存在完整付款則重用，不重複收款或佔位。
- **其餘 299 個學生沒有新增登入帳戶、報名、付款或佔位。300 個名冊檔案不代表 300 個已付款學生。**

Chloe 的訂單經現有 `create → send → respond → confirmPayment` 業務方法建立；不直接寫 Paid、學生課節或銷售 SQL。這是工具內的正式服務方法呼叫，並非冒稱 300 位使用者已做過 HTTP 登入及付款。沒有外部付款、寄件或訊息。

## 使用前準備

先明確建立原有三帳戶示例（`provisionDemoAccounts`），並從正常管理介面取得實際採用的六個課程、費用、四個教師及課室 ID。第一個課程、Maya／Leo 資源及原有 Leo 排課必須屬於原示例的固定 ID。未知資料不會被刪除以湊成全資料庫的精確數目；回報數量指這組採用的示例資料。

建立一個不包含帳密的私有 mapping JSON：

```json
{
  "courses": [
    {"id":"d3000000-0000-4000-8000-000000000301","feeId":"d3000000-0000-4000-8000-000000000401"},
    {"id":"第二課程的實際ID","feeId":"該課程費用的實際ID"},
    {"id":"第三課程的實際ID","feeId":"該課程費用的實際ID"},
    {"id":"第四課程的實際ID","feeId":"該課程費用的實際ID"},
    {"id":"第五課程的實際ID","feeId":"該課程費用的實際ID"},
    {"id":"第六課程的實際ID","feeId":"該課程費用的實際ID"}
  ],
  "teachers": [
    {"key":"maya","id":"d3000000-0000-4000-8000-000000000101"},
    {"key":"leo","id":"d3000000-0000-4000-8000-000000000102"},
    {"key":"ava","id":"Ava教師資源的實際ID"},
    {"key":"ethan","id":"Ethan教師資源的實際ID"}
  ],
  "rooms": [{"id":"d3000000-0000-4000-8000-000000000201"}],
  "startDate":"2026-10-16"
}
```

例如起始日為週五 2026-10-16，新增課程依次排為週六 10:00 Leo、週六 12:00 Maya、週日 10:00 Ava、週日 12:00 Ethan、週日 14:00 Maya；課室依 mapping 順序輪流使用。既有每堂計費的時長會沿用，其他模式使用 60 分鐘，工具只接受最多 120 分鐘的示例課節。所有預定老師／課室會與現有課堂及其他新課堂檢查衝突；衝突時停止，不搬動現有資料。

## 私有備份及明確執行

```sh
node sample/server/relational-demo.mjs \
  --database /absolute/private/beamal.sqlite \
  --mapping /absolute/private/centre-mapping.json \
  --backup /absolute/private/before-centre-demo.sqlite
```

三個參數均須明確提供。CLI 在首次／恢復寫入前建立 SQLite 一致性備份，支援正在使用 WAL 的資料庫；備份以 `wx`、`0600` 建立，已存在的目的檔案絕不覆蓋。目的資料夾須預先存在。程式也匯出 `backupRelationalDemo(databasePath, backupPath)` 供統籌先備份。不要把資料庫、備份或 mapping 放進 Git。

## 重跑及失敗邊界

1. 先核對原示例身分、明確 mapping、課程費用關係、現有連結、時間衝突及新學生 ID 所有權。
2. 第一個 transaction 只匯入 299 個正式學生及其歷史紀錄，保存 `relational_centre_demo_v1` 的 `profiles` 階段標記。
3. 第二個 transaction 使用 `store.mutateOnce`，包住新增排課、Chloe 帳戶連結及全部訂單流程。任何付款、版本或名額錯誤都會撤回這整個業務批次，包括新排課及帳戶連結。第一階段名冊保留，工具會報錯，不能當作整套建立完成。
4. 業務結果 ID 及固定鍵收據持久保存，再把階段標記改為 `complete`。若剛好在業務提交後中斷，下次會取得原收據，不重新收款或建立排課。
5. 完成後重跑只驗證既有紀錄並回報，不改姓名、課程、備註、課堂時間、密碼或歷史。mapping 或起始日期改變會拒絕；遺失紀錄不自動修補。學生後來退學會反映在 `activeStudents` 回報，不會被重跑重新啟用。

已存在但只覆蓋部分預定課節的 Paid 訂單會要求明確核對，不重複開另一張全額訂單。示例報價依每堂模式乘選定堂數，其餘模式使用所選費用的一個方案金額；沒有實作續期、退款、剩餘堂數或未確認的收費政策。

## 驗收

`node --test sample/server/tests/relational-demo.test.mjs` 使用隔離暫存資料庫，涵蓋：300 檔案、三個既有登入帳戶保留、四老師／六課程重用、原排課不變、2 Paid／7 課節、重跑與 mapping 衝突、未知 ID 保護、業務失敗撤回、現有時間衝突，以及在線備份私有權限及不覆蓋。

三個獨立 HTTP 登入的驗收會由管理員修改同一課節，再確認 Leo 與 Chloe 都取得新時間及同一課節身分；同時檢查老師不能讀全學生名冊，學生不能讀全班名冊。前端仍須實際讀取這些共用資料，不能用獨立的工作台預覽資料代替同步驗收。

## 2026-10-15 本機畫面驗收

已在既有本機資料上明確執行並先建立私有備份，保留原課程、費用、姓名及未知紀錄。管理員畫面確認六個課程、四位在職老師，以及包含 Chloe 的 300 筆正式學生資料（每頁 25 筆，共 12 頁）。停用的舊老師紀錄仍可在「全部」查看，預設只顯示在職成員。

三個示範登入身份已逐一實際登入。Leo 同時任教創意繪畫及水彩探索；Chloe 在這兩班共有七個已啟用課節、兩筆模擬付款訂單。管理員將 2026-10-16 的創意繪畫單一課節由 13:00 改成 13:30 後，Leo 的工作台、同一課堂的 Chloe 名單，以及 Chloe 的「我的課程」均顯示新時間。10-23 等後續課節仍為 13:00，沒有誤改整個學期。

再執行建立工具回報 `created:false`，仍為 300 位在學學生、兩筆已付款訂單、七個學生課節；沒有重複新增。學生個人資料頁只使用目前帳戶明確連結的 Chloe，不再顯示另一套假家庭或課包餘額。手機寬度檢查亦修正個人資料說明被擠在頭像欄內的問題。

這是本機共享人員、課程、排課及 Chloe 報名關係的驗收，不代表完整 SchoolTracs／Notion 要求已完成。其他 299 位只有名冊資料，尚未報名或付款；個別員工的細項權限表單亦仍屬介面示範，實際登入資料範圍繼續由既有帳戶連結及伺服器授權控制。
