# Courses／Fees 速度基準：2026-10-14

本輪只測共享服務讀取，未代表瀏覽器或實際手機的整體流暢度已通過。

## 方法

- 使用本機 Node v22.23.1；服務與讀取工具分開程序運行。機器同時有其他工作，未控制背景負載。
- 每組使用隔離的暫存 SQLite／WAL 資料庫及虛構管理員，真正登入後讀取。沒有使用 `sample/.data`，完成後移除暫存資料庫。
- 每個端點先預熱三次，再量度 20 次完整 HTTP 回覆；另量度 20 次同時讀取課程、費用及服務健康狀態。時間包含收齊資料，未包含瀏覽器解析或繪製。
- p50 是中位數；p95 是 95% 要求可在此時間內完成的界線。大小使用十進制 KB／MB，為未壓縮回覆。

## 初次結果

| 資料量 | 課程 p50／p95 | 收費 p50／p95 | 同時刷新 p95 | 每次課程＋收費資料 |
| --- | --- | --- | --- | --- |
| 100 課程／100 費用 | 7.6／12.4 ms | 3.3／6.7 ms | 21.7 ms | 121 KB |
| 1,000／1,000 | 48.1／94.1 ms | 13.7／32.0 ms | 128.8 ms | 1.21 MB |
| 1,000／1,100；100 費用各連十個課程 | 68.5／112.1 ms | 17.2／39.6 ms | 137.2 ms | 2.05 MB |

最慢單次讀取 178 ms；服務處理循環最大延遲約 159 ms，表示有短時間不能處理其他工作。讀取並未超過 500 ms，但此數字不能證明畫面沒有卡頓。

原始結果與程式版本指紋見 [JSONL](performance-baseline-2026-10-14.jsonl)。可重新量度：

```sh
node sample/server/benchmarks/course-fees.mjs
```

這個命令只建立暫存虛構資料，不修改實際測試資料庫。

## 尚未通過大量資料驗收

目前每五秒全量更新，最後一組每位使用者約讀取 24.65 MB／分鐘；同一筆費用亦會在課程內重複傳送。逐筆查詢關聯、完整回覆和序列化會隨資料量增加。

下一步先改批次查詢及減少沒有變動時的完整讀取，必要時分頁；然後用較多資料測瀏覽器與手機的搜尋、切頁、表格及拖動。需記錄資料量和實際操作結果，才可把大量資料的流暢度標為通過。

## 本輪改善：批次查詢與精簡刷新

以上「每五秒全量更新」描述的是初次基準時的狀態。本輪把逐筆資料庫讀取改成批次讀取，並加入 `/api/catalog`：完整回覆只傳一份收費資料，課程用收費識別碼連結；資料沒有變更時，只回覆版本狀態。

這樣可減少資料量越大、查詢次數越多的問題，也避免使用者每次刷新都下載同一份清單。舊課程及收費端點仍保留原有欄位、排序與權限。

資料庫查詢數量已用 80 筆資料的[獨立測試](../../sample/server/tests/catalog.test.mjs)核對上限：課程清單 3 次、收費清單 2 次、完整 Catalog 5 次、未變更 Catalog 2 次。這些數字只計清單資料查詢，不包括登入核對及交易開始／結束。

### 優化後首輪量度

沿用同樣三組虛構資料、隔離 SQLite、服務與讀取工具分開程序及每項 20 次讀取。新增完整／未變更 Catalog，以及未變更 Catalog 與健康狀態同時讀取。原始數據見[批次改善首輪 JSONL](performance-batch-2026-10-14.jsonl)，原來的比較基準仍見[初次基準 JSONL](performance-baseline-2026-10-14.jsonl)。

| 資料量 | 舊課程端點 p50／p95 | 舊收費端點 p50／p95 | 完整 Catalog 大小；p50／p95 | 未變更 Catalog 大小；p50／p95 |
| --- | --- | --- | --- | --- |
| 100 課程／100 費用 | 2.8／18.5 ms | 2.0／4.2 ms | 67.4 KB；3.5／6.8 ms | 96 bytes；1.8／3.3 ms |
| 1,000／1,000 | 13.0／17.1 ms | 6.0／7.4 ms | 673.1 KB；11.4／14.8 ms | 96 bytes；4.7／10.9 ms |
| 1,000／1,100；100 費用各連十個課程 | 40.1／194.6 ms | 15.7／36.2 ms | 785.1 KB；32.7／101.6 ms | 96 bytes；5.8／12.1 ms |

1,000 課程／1,000 收費的課程讀取中位時間由 48.1 ms 降至 13.0 ms，完整資料由原兩端點合共 1.21 MB 減至 673.1 KB。多對多例由 2.05 MB 減至 785.1 KB，少傳約 61.8% 的 JSON 內容；資料未變更時只傳 96 bytes。

若仍每五秒檢查一次，而且整分鐘沒有變動，未變更回覆合共約 1.15 KB JSON／分鐘／人，原多對多全量回覆約為 24.65 MB。這只是回覆內容的換算，未計 HTTP 標頭、其他功能要求或實際網絡開銷。

### 多對多尖峰與相同服務版本重測

首輪改善量度並非每項都比原基準快。例如多對多的舊課程端點 p95 由原基準 112.1 ms 升至 194.6 ms；舊課程、收費及健康狀態同時讀取，更曾出現 **465.5 ms** 的單次延遲，服務處理循環最大延遲為 **461.4 ms**。這項結果沒有刪除或以重測數字取代。

之後只對同一多對多規模重測，每項仍量度 20 次。[多對多重測 JSONL](performance-batch-many-repeat-2026-10-14.jsonl)與首輪檔案的五個服務模組 SHA256 完全一致，表示兩輪使用相同服務程式版本；兩輪虛構資料的筆數、關聯數及回覆大小亦一致。

| 量度項目 | 改善首輪 p50／p95／最大 | 相同版本重測 p50／p95／最大 |
| --- | --- | --- |
| 舊課程端點 | 40.1／194.6／199.8 ms | 16.6／21.7／22.0 ms |
| 舊收費端點 | 15.7／36.2／52.5 ms | 8.1／14.5／15.3 ms |
| 完整 Catalog | 32.7／101.6／247.7 ms | 12.8／18.7／26.9 ms |
| 未變更 Catalog | 5.8／12.1／18.4 ms | 2.8／3.4／3.5 ms |
| 舊兩清單與健康狀態同時讀取 | 36.0／113.0／465.5 ms | 22.0／31.5／63.2 ms |
| 未變更 Catalog 與健康狀態同時讀取 | 9.6／25.3／42.5 ms | 3.2／6.2／10.5 ms |

舊兩清單同時讀取的服務循環最大延遲，重測為 42.5 ms；未變更 Catalog 同時讀取的循環最大延遲，由首輪 32.1 ms 至重測 6.7 ms。

重測顯示此版本可以有較低延遲，但不能證明首次尖峰已解決。本輪沒有控制背景負載，也沒有取得足以確認尖峰成因的資料；**不把它歸因於未查證的背景工作或記憶體回收**。每組只有 20 次樣本，也不能當作正式部署的速度承諾。

### 如何重跑

在專案根目錄執行完整量度，保留 JSONL 輸出便可核對筆數、回覆大小、p50／p95／最大延遲及服務版本指紋：

```sh
node sample/server/benchmarks/course-fees.mjs > /tmp/beamal-performance-new-run.jsonl
```

此命令量度三組資料規模，每個舊端點及完整／未變更 Catalog 各 20 次，另量度兩種並行刷新。它複製包括 Materials 和 Attachments 在內的六個服務模組，使用隔離暫存資料庫，完成後清除資料，不使用 `sample/.data`。附件版本須同時解析安裝的依賴；快速 smoke 已核對腳本仍能運行，並非重新完成整組速度驗收。

只想確認量度腳本能運行，可執行快速 smoke（基本啟動及回覆檢查）：

```sh
node sample/server/benchmarks/course-fees.mjs --smoke > /tmp/beamal-performance-smoke.jsonl
```

`--smoke` 只使用 100 個課程及每項 3 次讀取，輸出亦會標明此模式。它不能代替完整效能量度或 UI／UX 驗收。

### 目前可確認與仍待驗收

可確認批次查詢次數有上限、完整 Catalog 減少重複資料、未變更回覆縮至 96 bytes，且原有資料格式與可見權限仍通過服務測試。

這些服務數據**未包含大量資料在瀏覽器內的解析、表格繪製、搜尋、切頁或拖動，也未代表實際手機或較慢網絡已通過**。仍需記錄大量資料下的實際操作及延遲結果，並追查可重現的尖峰，才可把「運作流暢、UI／UX 良好」的完整要求標為通過。
