## 3. 工作次序與階段出口

### 階段 A：先完成全系統 UI／UX

逐頁完成清單、詳情、表單、彈窗、分頁、選單、搜尋、篩選、排序、分頁切換，以及載入、空資料、錯誤、停用、成功、取消、返回等畫面狀態。不要只做好主頁而留下大量子頁或彈窗未整理。

主要次序：**課程＋費用＋時間表的聯合流程 → 產品 → 學生 → 會計 → 報告 → 員工**。銷售／訂單、老師工作台、學生端、Leads、訊息、渠道及設定按依賴穿插，但全系統都屬盤點範圍，不能永久漏掉。

- 已接通的真實功能與共用資料必須保留，不能為了 UI 先做退回另一套假資料。
- 尚未接通的操作先做好查看、輸入、欄位檢查、核對、取消及返回；最後提交可停用並在該處自然交代原因。不能為進入下一畫面而假顯示已儲存、已付款、已寄出或已同步。
- 不用滿頁「介面預覽」「虛構」「中期檢查」「QA」等工程字眼破壞示範；可用低干擾的「示範環境」標示，必要限制放在相關操作附近。
- 報告頁沿用使用者「先禁用按鈕」的階段安排；不能把它擴大為全系統按鈕都停用，也不能把永久停用當作最終功能完成。進入功能階段後，按總範圍逐項實作、驗收及啟用。
- 報告暫停用是階段性的明確例外：UI 製作與入口操作驗收分開記錄。不可到達的子畫面不得標為已從入口驗收通過；進入功能階段後補做真實入口、取消返回及錯誤恢復驗收，最終聯合驗收不保留此例外。

## 4. SchoolTracs 研究與第一性原理

使用者曾在 Chrome 開啟 SchoolTracs；啟動時先核對目前分頁及登入狀態，不假定舊登入仍存在。重要流程必須真的操作對照；舊截圖、文件及記憶只是索引。由同一位 Research Agent 控制參考網站，避免多位 Agent 互相跳頁。沒有必要時不修改參考網站資料；需要新增、刪除、付款或改權限等動作，仍遵守該動作的授權及工具規則。SchoolTracs 是研究依據，不能推翻 PDF 或 Beamal 最新需求。

每次研究至少記錄：入口、每一步、預選資料、主次操作、查看與編輯的分工、取消、返回、保存結果、涉及角色，以及當次畫面和未測範圍。

產品設計學習是 Goal 的工作內容：閱讀適用的 Product Design／UI／UX 技能及可靠第一手指引，沿用 UX-QUALITY.md 已記錄的任務分析、資訊組織、一致性、錯誤預防及焦點原則；有需要時再查閱來源。每個設計改動要連到實際問題、採用原則、方案取捨及操作證據。不能只抄術語、堆功能或聲稱已學會而沒有改善成果；Agent 走查不冒充客戶訪談，也不承諾跨對話永久學習。

用第一性原理逐項反問：

1. 使用者現在真正想完成甚麼？
2. 做這個決定最少需要哪些資料？
3. 哪些資料已經知道，可以沿用而不用再填再找？
4. 為甚麼這個按鈕放在這個對象及位置？移走會增加甚麼負擔？
5. 哪些步驟可以省略？哪些確認是為避免改錯堂、錯人、錯金額而必須保留？
6. 取消、失敗或完成後，用戶應返回哪裡繼續工作？
7. 這個安排適合管理員、普通老師及學生三種角度嗎？

## 5. 必須執行的 UI／UX 標準

- 以顧客日常工作安排資訊，清楚顯示目前位置、人物、課程、日期及下一步。
- 頁名已清楚時，不加重複介紹、口號或沒有幫助的副標題。例如 Products 下面毋須再寫「管理畫材、工具、套裝與庫存」。保留真正有用的身份、日期、狀態及必要限制。
- 老師個別權限放在 **員工 → 指定老師 → 對應設定**；不要放在時間表日常工具列。
- 老師／課室等低頻資源維護放在合理設定位置；實際指派則在新增／修改該堂時做。課型規則放課程或對應設定，不把所有設定塞進時間表。
- 清楚區分課程、整套定期排課、某日某堂、某學生該堂及訂單，不能為減少步數混成同一操作。
- 查看資料應有清楚查看入口；修改是明確意圖。單堂及往後課堂等修改範圍、付款金額等必要確認不可省略。
- 課程 → 課堂 → 名冊 → 訂單之間保留合理的課程、日期、課次、分頁、篩選、展開組別、捲動位置及焦點；取消後不要求重新搜尋。
- 從指定學生、員工或課堂開啟下一畫面，全程沿用確切 ID（資料的唯一編號），不能只改姓名卻借用第一筆示例的家庭、課堂或交易。資料未載入、不存在、撤權、換身份或來源未接通時，不回退其他人的示例；已開的私人視窗亦須在身份失效時關閉。未知帳戶狀態不等於未啟用，已有資料連結也不等於已激活。
- 瀏覽器 Back／Forward、關閉及取消屬同一返回流程；離開來源頁時不得留下舊課堂／訂單彈窗，亦不得讓延遲回覆重新打開。
- 窄畫面點側欄前往任何允許頁面後一律收起，包括 Fees 獨立網址。桌面保留原有開合選擇；所有頁面行為一致。
- Leads 的 Columns 使用拖動排序，手把是 **三條橫線**；保留顯示／隱藏、不可移除項目及合理的非拖動操作。
- 沒有文字貼邊、Logo 貼邊、錯位、重疊、裁切、不必要大空白或主操作被遮擋。主要內容區以桌面至少 24px、手機 16px 留白為專案預設，例外要有理由。
- 實際檢查 390px、768px、1280px，以及日常桌面視窗；確認是實際 CSS 寬度。中英文、長人名、課名、金額和日期都可讀。
- 頁面不可整體橫向溢出；闊表格可在自己的區域捲動。手機彈窗能看見標題、關閉、欄位及底部操作，並能捲到底。
- Tab 次序合理、焦點可見、彈窗焦點不跑到背景，關閉回原入口；純圖示按鈕須有可理解名稱，觸控操作足夠大。
- 主要觸控目標以 44×44 CSS 像素作專案設計目標；有需要再核對正式無障礙條件及例外，不憑幾張截圖宣稱全面認證。
- 載入、真空資料、篩選無結果、錯誤及無權限要分得清；未知數不能填 0，未載入不能寫沒有學生。
- 儲存有即時回饋並防止重按；失敗保留草稿和可理解的修正方法。背景更新不能覆蓋正在輸入的內容。
- 每個改動都查同類問題有沒有出現在其他頁面，避免只修單一截圖。
- 不套用所有任務必須三次點擊完成的規則；衡量完成任務、搜尋、重填、決定、等待及恢復成本。

## 10. 多 Agent 工作方式

按工具實際可用名額分工，不假稱有未啟動的 Agent：

1. **主 Agent**：管理總目標、依賴、來源衝突、整合、優先次序、待決事項及對使用者的報告。
2. **Research Agent**：實際操作 SchoolTracs，記錄行為、畫面、設計推論及未測範圍；同一時間只有一人控制參考頁。
3. **製作 Agent**：擁有清楚指定檔案／模組，完成小而可驗收的工作；不得覆蓋其他人的修改。
4. **獨立驗收 Agent**：由沒有製作該切片的人對照要求、程式及實際操作驗收，找跨頁／跨角色副作用。

共用 `src.js`、資料庫遷移或同一共享模組同時只安排一位寫入者；獨立工作並行，依賴及整合按順序。研究、製作與驗收的證據分開，不用同一位 Agent 自稱測過來代替獨立審查。

每位製作 Agent 都要知道自己負責的檔案／模組及「不是獨自在此專案工作」；不得 revert／覆蓋別人的改動。由主 Agent 協調共享資料契約、整合及交接。工具有幾個實際名額便用幾個，不為湊角色開超量工作或讓多位同時控制同一頁。
